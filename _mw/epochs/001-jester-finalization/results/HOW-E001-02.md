## Assembly contract

This is a bounded mechanism repair. It must preserve the MiniDoc 0.1 feature boundary while closing three exact correctness/evidence gaps: later user intent must outrank stale asynchronous Open completion; edits made after an earlier Save/Discard decision must not be discarded by a late candidate; and the installed PDF lifecycle gate must distinguish successful installed PDF admission/render from a caught failure.

No Research, new persistent state, background worker, cancellation framework, network effect, file association, or target feature expansion is required.

## Accepted mechanism

### Open-intent and document-state freshness

The shell owns two independent monotonic generations:

1. **open-intent generation** — every user/programmatic replacement intent obtains a new identity; New and a later Open invalidate any earlier unresolved Open attempt;
2. **document-content generation** — every material edit/formatting mutation advances the current document generation.

An Open attempt captures its open identity and the current document-content generation after the applicable unsaved-change decision and immediately before candidate work begins. DOCX parsing and PDF session acquisition occur as candidate work. After every asynchronous boundary and immediately before current-session replacement, admission requires both:

- the attempt is still the current open intent; and
- the current document-content generation still equals the generation that the earlier unsaved-change decision authorized.

If a later New/Open superseded the attempt, the candidate is discarded/closed without changing current presentation/status. If the current document changed while the candidate was loading, the candidate is not admitted; the current document and its new unsaved edits remain authoritative and the user receives a bounded “open cancelled because current document changed” status/message. The product does not silently reuse an earlier Save/Discard authorization for later edits.

This freshness rule applies to candidate admission itself and is separate from the existing PDF-render freshness fence. Stale Open work may finish internally, but it has no Authority to replace the current document.

### Error/status freshness

A stale Open attempt also lacks Authority to overwrite status or present an error for a newer current document/intent. Open failure is surfaced only while that attempt remains current. Candidate resources acquired by a stale PDF attempt are disposed before return.

### Installed PDF-path success oracle

The existing verification-only startup route remains non-persistent and does not become a user feature. Its internal open path returns an explicit success result. PDF open success requires candidate admission **and successful first-page render**, not merely a caught method return.

The verification-close launch mode uses process exit semantics as the oracle:

- exit code `0` only after the requested file is successfully admitted/rendered through the normal installed shell path and the main window then closes normally;
- a failed verification-mode open/render terminates with a non-zero process exit code;
- `scripts/verify-windows.ps1` requires the process exit code to be zero in addition to the existing termination/residue assertions.

Normal interactive launches retain ordinary UI error handling; the non-zero exit code is specific to the explicit verification mode.

| Choice | State | Boundary |

| monotonic local open-intent identity | `FIXED` | later New/Open supersedes earlier unresolved Open |
| document-content generation | `FIXED` | any edit after the captured unsaved-change decision blocks late candidate admission |
| stale candidate disposal/no-current-UI mutation | `FIXED` | stale PDF candidate resource is disposed; stale errors/status are suppressed |

| verification process exit oracle | `FIXED` | zero on successful verification-close path, non-zero on caught open/render failure |

No `UNRESOLVED_BLOCKING` design choice remains in this slice.

## Verification strategy

A cold verifier must establish, on the exact candidate:

- two open tickets cannot both remain current after a later replacement intent;
- a document-content generation change invalidates a previously captured candidate admission;
- stale candidate completion cannot release/replace the current session or overwrite newer status;
- the installed verification route returns success only after initial PDF render success;
- Windows verification fails on non-zero verification-mode exit and still proves normal success termination/install/uninstall residue on a valid fixture;
- existing first-party dependency, zero-persistence, process-exit and Product capability boundaries remain unchanged.

Pure transition-generation semantics should receive deterministic semantic checks where practical; WPF/WinRT timing need not be inflated into a new scheduler solely for testability.

## Provocation trace

### P1 — “Let the failed visitor evict the current tenant first”

**Wanted:** try opening a document that cannot be admitted and ask whether MiniDoc preserves the already-open current session until the replacement proves it exists.

**Actually observed:** `MainWindow.OpenPathAsync` routes by extension. On the DOCX branch it calls `ReleasePdf()` **before** `DocxCodec.Open(path)` succeeds. On the PDF branch `OpenPdfAsync` calls `ReleasePdf()`, clears `_docxSession`, rewrites `_currentPath`, clears `_dirty`, and only then awaits `PdfSession.OpenAsync(path)`. The outer catch reports “Open failed” but does not restore prior state.

**What happened in source semantics:** a failed replacement attempt can partially dismantle the current session before the replacement has been established. A failed DOCX open while a PDF is current discards the current PDF session. A failed PDF open while an editable DOCX is current clears its `_docxSession` and path while the old editor document/mode can remain visible, leaving a structurally inconsistent UI/session posture.

**Evidence/reproducer:** `src/MiniDoc/MainWindow.xaml.cs` at `b2caf...`: `OpenPathAsync`, `OpenPdfAsync`, outer catch. No mutation was performed.

**Limit:** source establishes ordering/state mutation, not a particular Windows visual symptom.

**Jester remark:** the replacement tenant failed the credit check, but the landlord had already bulldozed the old apartment. Elegant.

### P2 — “Yesterday's PDF ghost paints tomorrow's page”

**Wanted:** assume asynchronous rendering has supernatural rights after the user has already moved to another document.

**Actually observed:** `RenderPdfAsync` uses one shared `_pdfRendering` flag and awaits `_pdfSession.RenderPageAsync(...)`, then unconditionally writes `PdfImage.Source` and `StatusText`. `ReleasePdf()` can clear/dispose the current session while an awaited render is in flight. New/Open remain separate actions; there is no generation/session token or stale-completion check. A second PDF open can establish a new `_pdfSession` and call `RenderPdfAsync`, but if the old render still owns `_pdfRendering = true`, the new render returns immediately. The old continuation can then write its old bitmap into the now-current PDF host.

**What happened in source semantics:** render completion is not bound to the session/revision that commissioned it. A stale asynchronous completion can outlive its owning session and mutate current presentation state.

**Evidence/reproducer:** `src/MiniDoc/MainWindow.xaml.cs` at `b2caf...`: `RenderPdfAsync`, `OpenPdfAsync`, `ReleasePdf`, New/Open paths; `src/MiniDoc/Pdf/PdfSession.cs` shows render is genuinely awaited.

**Limit:** exact event timing remains runtime-dependent; the missing freshness guard is source-factual.

**Jester remark:** exorcism currently consists of setting a field to null and hoping the ghost respects variable scope.

### P3 — “Add a column, deny its citizenship”

**Wanted:** make the table grow cells while keeping its formal column registry frozen and see whether the object contradicts itself.

**Actually observed:** `TableEditor.CreateTable` creates both `Table.Columns` descriptors and row cells. `AddColumn` appends one cell to every row but never adds a `TableColumn`; `DeleteCurrentColumn` removes row cells but never removes the corresponding `TableColumn`. The DOCX writer ignores `Table.Columns` and serializes based on row cell counts, so the saved file can remain rectangular even while the live WPF table carries stale column-descriptor state.

**What happened in source semantics:** live presentation metadata and serialized logical table width can diverge after column edits.

**Evidence/reproducer:** `src/MiniDoc/Editor/TableEditor.cs` and `src/MiniDoc/Docx/DocxFlowWriter.Table.cs` at `b2caf...`. Deterministic structural reproducer: create 3×3 table → `Table.Columns.Count == 3`; call `AddColumn` → each row has 4 cells while `Table.Columns.Count` remains 3.

**Limit:** this Report does not claim a particular WPF layout failure; it records the internal divergence.

**Jester remark:** the fourth column exists physically but immigration refuses to issue paperwork.

### P4 — “The compatibility viewer advertises a cinema and delivers a cardboard sign”

**Wanted:** take the accepted claims about previews/notes literally and look for the machinery that must exist to make them true.

**Actually observed:** current Target HOW says compatibility mode can resolve embedded raster relationships, show safe image previews/fallbacks, and expose safely resolved footnote/endnote body text. `docs/COMPATIBILITY.md` says an existing package preview can be surfaced. But `DocxCodec.BuildResult` passes only the main-document `XDocument` to `DocxFlowReader.ToReadOnly`. That function has no package/relationship/media/notes input; it extracts text and emits generic marker strings such as `[Graphic/chart/diagram object — ... preview unavailable ...]` and `[Footnote reference — source is read-only]`.

**What happened in source semantics:** the current Product implements safe marker/text fallback, but accepted Target HOW and public compatibility summary describe relationship-backed preview/note behavior that this implementation path cannot perform.

**Evidence/reproducer:** `_mw/knowledge/TARGET-HOW.md`, `docs/COMPATIBILITY.md`, `src/MiniDoc/Docx/DocxCodec.cs`, `src/MiniDoc/Docx/DocxFlowReader.cs` at the admitted Product Baseline.

**Limit:** Target WHAT uses permissive language (`may`) for these richer presentations; this observation therefore exposes a Product/Target-HOW/documentation reconciliation issue rather than establishing a missing mandatory user outcome by itself.

**Jester remark:** a poster saying “picture preserved somewhere backstage” is not, strictly speaking, the picture.

### P5 — “Find the case-sensitive switch in the invisible dimension”

**Wanted:** obey Target HOW's phrase “optional case-sensitive toggle” and try to locate the toggle without using spiritual perception.

**Actually observed:** Target HOW describes search as case-insensitive by default with an optional case-sensitive toggle. `MiniDoc.Editor.TextSearch` accepts a `caseSensitive` parameter, but the UI exposes no toggle and `MainWindow.MatchCase()` is hard-coded to `false`.

**What happened in source semantics:** the lower-level mechanism supports the variant, while the accepted current UI mechanism claim overstates what the Product exposes.

**Evidence/reproducer:** `_mw/knowledge/TARGET-HOW.md`, `src/MiniDoc/MainWindow.xaml`, `src/MiniDoc/MainWindow.xaml.cs`, `src/MiniDoc/Editor/TextSearch.cs` at `b2caf...`.

**Limit:** Target WHAT does not require case-sensitive search, so the downstream owner may either realize the toggle or correct Target HOW; the Jester chooses neither.

**Jester remark:** excellent toggle. Zero pixels, zero bugs, immaculate minimalism.

### P6 — “The rescue copy catches fire; report only the first fire”

**Wanted:** let an overwrite fail and then make the best-effort restoration fail too. Ask what epistemic state the user receives.

**Actually observed:** `DocumentWriter.WriteExplicitTarget` keeps prior bytes in memory and, on write failure, attempts restoration. A restoration exception is swallowed so the original write exception remains authoritative. The caller displays that original exception as “Save failed”. If restoration also failed, the destination may be damaged or partially rewritten, but the application does not surface that stronger uncertainty.

**What happened in source semantics:** the implementation correctly avoids claiming atomic save, but an ordinary two-stage write+restore failure can create `UNKNOWN` target integrity while the user-facing error path does not distinguish it from an ordinary failed save with successful restoration.

**Evidence/reproducer:** `src/MiniDoc/Storage/DocumentWriter.cs` and `MainWindow.SaveCurrent` at `b2caf...`; Target WHAT already documents non-atomic process/power failure but not this swallowed restoration failure state.

**Limit:** this is a source-level failure-semantics observation; no filesystem fault injection was executed.

**Jester remark:** the fire brigade crashed into the building, but the incident report preserves the dignity of the original toaster fire.

## Provocation trajectory

### P1 — Let the dead PDF request come back and seize the throne

**Wanted to try:** start opening a slow PDF, then make a later user action while the first open is still waiting. Ask whether the earlier request understands that it is yesterday's news.

**Actual observation:** `Open_Click` performs `ResolveUnsavedChanges()` and then awaits `OpenPathAsync`. `OpenPdfAsync` awaits `PdfSession.OpenAsync(path)` **before** replacing current state. There is no open-operation identity, cancellation/freshness token, disabled Open/New boundary or post-await “is this still the user's current intent?” check. When the candidate session eventually opens, it calls `ReleasePdf()`, clears DOCX session state and becomes current.

**What happened conceptually:** the pass-1 render-freshness fence protects already-started **render** callbacks, but candidate **open** itself is not fenced. A slow earlier PDF open can therefore complete after a later `New` or later PDF-open intent and replace that later state. Completion order can become accidental user-intent authority.

**Evidence:** exact Product `src/MiniDoc/MainWindow.xaml.cs` at `4a7c...`: `Open_Click`, `OpenPathAsync`, `OpenPdfAsync`; render freshness uses `_pdfRenderRequest`, while open admission has no corresponding request identity.

**Jester remark:** the zombie callback now respects the picture frame but still owns the front-door keys.

### P2 — Sign the discard permission, then let the user write another paragraph while the courier is downstairs

**Wanted to try:** exploit the gap between the unsaved-change prompt and asynchronous PDF admission. The user changes their mind by editing, not by clicking Cancel.

**Actual observation:** unsaved changes are resolved **before** the file picker and before `PdfSession.OpenAsync`. While PDF open awaits WinRT I/O, the prior editable DOCX remains the active WPF document. Nothing in the observed shell freezes editing or revalidates dirty state immediately before candidate admission. If the user edits during that interval, `Editor_TextChanged` can set `_dirty = true`; when the PDF candidate later succeeds, `OpenPdfAsync` replaces session state and sets `_dirty = false` without a second unsaved-change decision.

**What happened conceptually:** the earlier Save/Discard decision can outlive the state it authorized. A new unsaved edit can appear after authorization but before replacement and then be discarded by the late candidate admission path.

**Evidence:** same exact shell flow: `ResolveUnsavedChanges()` precedes all asynchronous open work; `OpenPdfAsync` resets `_dirty` after its await and does not call `ResolveUnsavedChanges` or compare an edit/session generation.

**Limitation:** no live UI timing reproducer was executed in Observation mode. The report establishes the reachable state-order from source, not measured human timing frequency.

### P4 — Pay the funeral director when the patient merely reaches the morgue door

**Wanted to try:** see whether the Windows lifecycle evidence can congratulate itself even if the installed UI failed to complete the promised PDF-open/render path.

**Actual observation:** `scripts/verify-windows.ps1` starts installed MiniDoc with `--verify-close-after-open <sample.pdf>`, waits for process termination and checks residue. `App.Application_Startup` awaits `window.OpenInitialPathAsync(path)` and closes the window afterward. `OpenPathAsync` catches open/render-path exceptions internally and returns normally; `OpenInitialPathAsync` returns only `Task`, not a success result. The verification script does not inspect a Product success marker or exit code distinguishing successful PDF UI admission/render from a caught open failure.

**What happened conceptually:** the lifecycle gate strongly proves install ownership, process termination and uninstall cleanup after an attempted PDF path, while its wording/evidence narrative can be read more strongly as proving that installed UI open/render itself succeeded. Separate `MiniDoc.Checks` does exercise `PdfSession` rendering on the fixture, so this is not evidence that PDF rendering is broken; it is a potential oracle gap between two evidence claims.

**Evidence:** exact `scripts/verify-windows.ps1`, `src/MiniDoc/App.xaml.cs`, `src/MiniDoc/MainWindow.Startup.cs`, and `OpenPathAsync` catch behavior at `4a7c...`.

### P5 — Save over an elephant wearing a `.docx` hat

**Wanted to try:** point Save As at an absurdly large existing target and watch the “no temp file, keep prior bytes in memory” dignity ritual.

**Actual observation:** `DocumentWriter.WriteExplicitTarget` reads the entire pre-existing target through `File.ReadAllBytes` before attempting overwrite, with no target-size bound at this boundary. The incoming generated DOCX is bounded by the editor/package model, but the pre-existing chosen destination need not have been opened or validated by MiniDoc.

**What happened conceptually:** a user-selected enormous existing target can demand correspondingly enormous recovery memory before any write. This follows directly from the accepted memory-staged recovery design; whether a target-size guard is worth adding is an engineering/product decision, not a Jester verdict.

**Evidence:** exact `src/MiniDoc/Storage/DocumentWriter.cs` at `4a7c...`.

**Jester hypothesis:** the product has deliberately bought “no temporary save artifact” with a potentially ugly memory bill at overwrite time. This may be acceptable for 0.1.
